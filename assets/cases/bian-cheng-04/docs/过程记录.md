## 第 2 步 · 照做（先 CSS 版，再 JS 版 —— 严格按手册给的顺序）

### 阶段1 · 素材与数据准备

**做了什么**：`gen_works.py` 生成 20 件作品数据 + 20 张自绘 SVG；`measure_grid_waste.py` +
`measure_grid.mjs` 把普通网格的代价量出来。

**输入 → 输出**：

| 输入 | 输出 |
|---|---|
| 设计好的 20 条作品元数据（标题/类别/年份/长宽比/配色/构图/批次） | `输入素材/works.json`、`输入素材/posters/p01–p20.svg` |
| 同一批 16 张图，普通网格 3 列 | `产物/普通网格对照组.html` → 实测**空白 2,262px / 占网格面积 23.3%** |

**为什么先做这一步**：痛点的说服力来自数字。"普通网格很难看"要变成
**"16 张图里，矮卡片下面一共空了 2,262px，占这块版面的 23.3%"**，后面每一步才有靶子。

**踩的坑**：静态对照组页面里图全是空白 —— 因为"图片解码后淡入"依赖 JS 加 `.ready`，
而对照组是纯静态页。修法：把淡入的初始态写成 `html.js .shot img{opacity:0}`，
**拿"JS 是否可用"当开关**，JS 挂了图照样能看见。

### 阶段2 · CSS columns 简单版

**做了什么**：`build_columns.py` —— 布局 8 行 CSS，**零行 JS 在做位置**。

**结果**：`最终产物/瀑布流作品集_CSScolumns版.html`（101.4 KB）

| 指标 | 值 |
|---|---|
| 各列高度 | `[2275, 2537, 2894]` → 极差 **619px** |
| 卡片高度去重 | **13 种**（281…788px），最高/最矮 **2.80** |
| 同列间距 | 全部 20px（没有对齐空洞） |
| 无重叠 / 0 外链 | ✅ / ✅ |

**★ 量出的代价**：点"加载更多"追加 4 件 → **16 张旧卡片里有 11 张移动了位置**。

### 阶段3 · JS 算列高精确版

**做了什么**：`build_masonry.py` —— 把手册那句"算每列高度，再决定卡片放哪一列"落成**三步、≈20 行**；
加了 `__masonryDebug` 记账与"列高标尺"签名元素。

**两个"量而不是猜"的方法要点**：卡片高度在**离屏容器**里、以**目标列宽**实测；
列宽读**第一列的实际渲染宽度**，不用公式近似值。

**结果**：`最终产物/瀑布流作品集_JS算高版.html`（103.2 KB）

| 指标 | 值 |
|---|---|
| **每次分配都命中最短列** | **32/32** |
| 各列高度 | `[2659, 2391, 2655]` → 极差 **268px**（CSS 版 619px） |
| 追加 4 件后旧卡片位移 | **0 / 16（原地不动）** |

**踩的坑**：`relayoutAll()` 一开始读 `board` 的 DOM 顺序重建 —— 但瀑布流把卡片**按列分组**了，
DOM 顺序已经不是作品顺序，点列数切换后视觉顺序会乱。改成**始终以 `WORKS` 顺序为准**。

### 阶段4 · 功能与视觉核验

**做了什么**：`verify_masonry.mjs`（headless Chrome + CDP，显式端口，零第三方依赖），
对两版各跑 15 项测量判据 + 出图 11 张/版；`diagnose_hover_cue.mjs` 排除"假 hover 反馈"。（判据在审查打回后扩到 **17 项公共**，见下「审查打回与修复记录」。）

**结果**：初版**两版各 15 项全部 PASS**；审查打回并修复后扩到 **CSS 17 项 / JS 20 项**，仍全部 PASS。

**踩的坑（3 个，都很典型）**：
1. **核验脚本自己有 bug**：属性名 `h` 写成 `height` → `NaN` → 去重后"只有 1 种高度"。
   教训：报出这种反常结果时，**先怀疑测量代码**。
2. **骨架截图拍晚了**：截图挪到 `Page.navigate` 之后的第一个动作，并把握手等待加到 130ms。
3. **hover 量不到**：鼠标事件用**视口坐标**，而目标卡片在视口外；先把卡片滚进视口就通过了。
   另留 `CSS.forcePseudoState` 兜底并在日志里标明生效方式。

## 与手册的偏差 / 需要说明的地方

| 项 | 说明 |
|---|---|
| 作品图用**自绘 SVG** 而不是 picsum.photos | 任务书允许两者，选自绘的三条理由见 `输入素材/来源说明.md`：① 精确控制长宽比（痛点需要）；② 0 外链（"发出去就能开"）；③ 零版权风险（P15 第 5 条） |
| 作品数 **20** 件（首屏 16 + 加载更多 4） | 高于任务书"≥12 张"的要求。多出的 4 件是**为"加载更多"准备的**——否则"追加内容"没有真实内容可加，两条路线的代价差异就测不出来 |
| 加了"列数切换 2/3/4"与"列高标尺" | 手册没要求。列数切换是为了验证响应式与重排；**列高标尺是 JS 版的教学签名元素**，把"算法在干什么"变成肉眼可见 |
| `SIM = { latency: 600, failNext: false }` | 静态页面没有后端，"加载状态"需要一个可调的模拟层。`failNext` 是**刻意的调试开关**，用来演示"出错了"那一态（审查配置里已说明） |
| **单文件里唯一的外链是"换另一版看看"这个导航链接** | 静态扫描：两版各 **0 个 `<link>`、0 个 `<script src>`、20 张图全部 `data:image/svg+xml` 内联**；非 `data:` 的 `src`／`href` 只有一条——工具栏上指向同目录另一个 HTML 的 `<a href>`。**它是一条导航链接，不是资源依赖**：把任意一个 HTML 单独拷走，页面照常完整显示（20 张图都在），只有那个"换一版"的链接会失效。<br>❗**这句原先有漏洞**（审查方指出）：我当时只扫了 `src`／`href`，但核验脚本的选择器是 `link[href]/script[src]/img[src]`，**不含 `a[href]`**；而卡片本身当时正是 `<a class="shot" href="#">`。说"只有一条"是对的（`a[href]` 也确实只有那条导航链接 + 20 个卡片锚点，只是卡片锚点没被数进来），但**据此说"不存在假链接"就是越界推论**——事实是当时有 20 个占位假链接（见下条）。现已把 `a[href]` 纳入扫描。 |

## 环境限制（本轮实测到的，建议记入 `环境限制备忘.md`）

| 限制 | 现象 | 应对 |
|---|---|---|
| **C 盘已满（剩余 0 GB）** | Git Bash 的 `/tmp` 与 PowerShell 的 `%TEMP%` **都写不进文件**：报 `No space left on device` / 「磁盘空间不足」。管道输出（如 `ls \| tail`）也偶发同样报错 —— **一开始误判成"管道缓冲问题"，实际是磁盘满了** | 中间产物一律写在**案例目录（D 盘）内**；截图与 JSON 全部落在 `最终产物/`；避免往 `%TEMP%` 拷大文件。`D` 盘剩约 5 GB |
| Chrome 用 `--remote-debugging-port=0` 不稳 | 偶发读不到 `DevToolsActivePort`（EBUSY）、或直接"Chrome 未就绪"；机器上同时有 29 个 chrome 进程 | 核验脚本改用**显式随机端口（9500+rand）+ HTTP 轮询 `/json/version`**，并加 2–3 次重试 |
| headless 下 hover 状态偶发不推给渲染器 | `isHover=false`，样式无变化 | 先把目标卡片**滚进视口**（鼠标事件用的是视口坐标）再派发；仍失败则回退 `CSS.forcePseudoState` 并在日志里标明生效方式 |
| PowerShell 控制台中文显示乱码 | 读 UTF-8 文件时中文变乱码 | 文件本身没问题；读内容改用 `py -X utf8` 或 Read 工具 |

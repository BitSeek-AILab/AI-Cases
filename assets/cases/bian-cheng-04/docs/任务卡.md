## 要解决什么（承接痛点卡）

把"**长短不一的图片用普通网格排 → 每行对齐、留一堆空白（实测空白 2,262px / 占网格面积 23.3%）、很难看**"
变成"**图片自然下落、填最短的列、卡片高度真的不一、没有对齐空洞**"，
并且**两条实现路线各出一版、说清各自代价**。

具体四件事：

1. **真的瀑布流**——卡片高度不一；新卡片落到**当前最短的列**（可被脚本证明）。
2. **三种交互齐活**——hover 反馈 / 加载状态（骨架屏 + 图片淡入 + "加载更多"）/ 瀑布流本身（手册 P08）。
3. **两条路线各一版**——CSS `columns` 版（简单快）与 JS 算列高版（精确、追加不跳），**并量化两者的代价差异**。
4. **手机 390px 可读不横滚**（且不靠 `overflow-x:hidden` 藏溢出）。

## 手册方法拆解（照做纪律：手册说啥做啥）

| 手册原句 | 本案例怎么落地 |
|---|---|
| 「卡片像水一样填满**最短的列**」 | JS 版实现"最短列优先"分配，并**记录每次分配前的各列高度**，事后校验每次都落在 `argmin` 列 |
| 「普通网格每行对齐」 | 阶段1 先**实测**普通网格的空白代价（2,262px），作为"为什么要瀑布流"的证据 |
| 「图片多、长短不一」时很适合 | 输入素材构造成 **20 件（首屏 16 件）、长宽比 0.517–1.786 混排**（横竖方混合，跨度 3.46 倍），制造真实的"长短不一" |
| 「简单版可用 CSS `columns`」 | 阶段2：`column-count` + `break-inside:avoid` 版 |
| 「更精确的版式通常用 JS 计算每列高度，再决定卡片放哪一列」 | 阶段3：JS 逐张算高度、选最短列，并暴露 `__masonryDebug` 供核验 |
| 「交互是让用户知道'可以做、做完了、出错了'」 | hover → "可以做"；骨架屏/淡入/加载更多三态（加载中·完成·失败重试）→ "做完了 / 出错了" |
| P15 交付六条自检 | 逐条做成验收点（见下） |

## 验收点（供自检与审查）

对照手册 P09 / P08 / P15 逐条验收：

- [ ] **卡片高度真的不一**（红线）：渲染后所有卡片高度去重后**≥ 8 种不同值**；最高/最矮之比 ≥ 1.5（证明不是把图裁成一样高）。
- [ ] **真的填最短列**（红线）：JS 版 `__masonryDebug` 里**每一次分配的目标列 == 分配前各列高度的 argmin**（100% 命中）；且渲染后各列总高差 ≤ 最矮一张卡片的高度。
- [ ] **不是普通网格**：两版都**没有"每行对齐"的空洞**——逐列量：同列相邻卡片之间无异常空隙；普通网格对照组的空白量（2,262px）明显大于瀑布流版。
- [ ] **无错位**（红线）：任意两张卡片的包围盒**不重叠**（面积交为 0）；无卡片越出容器。
- [ ] **hover 有反馈**（红线）：`getComputedStyle` 在 `:hover` 前后**有可见变化**（transform / 遮罩 opacity），且不是 `display:none` 一言不合藏起来。
- [ ] **加载状态齐全**：① 首屏骨架屏 → 内容替换（实测：0ms 时 16 张骨架、300ms 后替换为 16 张卡片）；② 图片解码后 `opacity` 从 0 到 1 淡入（实测 16/16 张 `opacity=1`）；③"加载更多"有 **loading / done / error 三态**，且能真的追加卡片（实测 16 → 20 张）。
- [ ] **手机可读**（红线）：390px 下 `innerWidth === 390` 且**摘掉 `overflow-x:hidden` 后 `doc.scrollWidth ≤ 390`**；320px 兜得住；正文字号 ≥ 12px。
- [ ] **真单文件 + 能打开**：两版各 **0 个外部资源引用**（不含 `data:`），拷走一个 HTML 双击能开（本轮用 headless Chrome 实测）。<br>※ 如实说明：单文件里**唯一**一条非 `data:` 的引用是工具栏上"换另一版看看"的 `<a href>`（指向同目录另一个 HTML）。它是**导航链接、不是资源依赖**——单独拷走一个文件，20 张图照常显示，只有这条链接会失效。
- [ ] **内容真实**：20 条作品的标题/类别/年份来自 `works.json`，无 Lorem、**无占位假链接**。<br>※ "无占位假链接"的判据必须**扫 `a[href]`**：空 / `#` / `javascript:` 一律算占位假链接。**只扫 `link/script/img` 是看不到它的**（本案例第一版就栽在这里：卡片是 `<a href="#">`，扫描器结构上看不见，却被误判成"不存在假链接"）。<br>※ 另加**回归判据**：**点击卡片不得产生任何导航/回顶**（旧版 `href="#"` 点击会把 `scrollY` 打回 0、URL 变成 `...html#`）。
- [ ] **授权清楚**：不含任何第三方图片/商标；20 张图均为脚本自绘 SVG。
- [ ] **两条路线的代价被量化**：追加内容时 CSS 版"旧卡片移动数"与 JS 版"旧卡片移动数"都实测出来（作为选型依据）。
- [ ] **风格统一**：两版共用同一套配色 / 字体 / 卡片样式。

## 红线

- 不许只描述不产出：`最终产物/` 必须有**两个真能打开的 HTML**。
- 必须做**视觉/功能核验**：headless Chrome 打开、截图、实测高度不一/填最短列/无重叠/hover 有变化/手机 390，**不能只读代码**。
- **"卡片高度不一"与"填最短列"必须用测量取证**——不能靠"长得像瀑布流"。
- 手机 390px 必须不横向滚动——且**不能靠 `overflow-x:hidden` 把溢出藏起来**（核验脚本专门摘掉再看一遍）。
- 截图存证，过程记录逐步写。
- 不许引第三方 masonry 库 / 不许抄现成瀑布流 demo 的代码；算法按手册那句"算每列高度选最短列"自己实现。
- **不许出现占位假链接**：没有详情页就不许把卡片写成 `<a href="#">`；也不许在 hover 文案里承诺做不到的事（例如写"查看作品"却没东西可看）。**核验时必须扫 `a[href]`**，并实测点击不产生导航。

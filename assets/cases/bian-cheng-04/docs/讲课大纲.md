# 讲课大纲 · 案例编程-04 瀑布流作品集页

> 手册只给了主题（P09 一页"瀑布流"），本大纲把主题展开成可直接讲的 6 段。
> 每段都写清：**讲什么、为什么这时候讲、用什么把它讲实**。

---

## 这节课要学员带走的判断

**"排得整齐"和"排得好看"是两件事。**

普通网格追求的是"每行对齐"——整齐；但图片长短不一时，对齐的代价是**一行里最矮的那张下面会空一块**。瀑布流放弃"每行对齐"，换来"没有空洞"。
本案例的全部技术选择，都是为了跨过这条线：**让长短不一的图片自己形成版面的节奏，而不是被网格切成整齐的格子。**

---

## 第 1 段 · 先看手上的料（4 分钟）

**讲什么**：开工前第一件事不是打开编辑器，是**清点素材并量出代价**。

- 现场打开 `输入素材/works.json`：**20 件作品（首屏 16 件）**，每条含标题 / 类别 / 年份 / 长宽比 / 配色。
- 关键：这 20 张图的**长宽比是混的**（横的、竖的、方的），现场把比例念出来：
  - 最横的 **1.79:1**（p02 夜行列车），最竖的 **0.52:1**（p06 山海经，≈ 1:1.93）——**横向差 3.46 倍**。
- 带着学员看 `阶段1_素材与数据准备/产物/数据核对报告.txt` 的结论：
  - 20 条数据、长宽比最小 0.517 / 最大 1.786；
  - 20 张自绘 SVG 的 viewBox 与 `works.json` 声明**一一对上**（脚本交叉核对）。

**为什么这时候讲**：这个"长宽比差 3.46 倍"就是本案例的**全部问题来源**。不先量出来，"为什么要瀑布流"就只能靠嘴说。

**互动提问**：如果这些图**全是同一个长宽比**，还需要瀑布流吗？（答：不需要，普通网格就够了，还更快——**技术选择要跟着素材走，不是跟着流行走**。）

## 第 2 段 · 先把"普通网格的代价"量出来（5 分钟）★先立靶子

**讲什么**：**不要一上来就讲瀑布流怎么做，先让学员亲眼看到"不做瀑布流有多难看"。**

现场跑 `measure_grid_waste.py`，用**同一批首屏 16 张图**排一个 3 列等宽网格，量三件事：

| 量什么 | 怎么量 | 结果 |
|---|---|---|
| 每行按最高的卡片对齐 | 逐行取 `max(卡片高)` | 行高被最高的那张决定 |
| 矮卡片下方留了多少白 | `行高 − 卡片高`，逐张累加 | **2,262px** |
| 这些白占了多少地方 | 空白 ÷ 网格面积（Σ行 行高×卡片数） | **23.3%** |

同时把对照组页面（`产物/普通网格对照组.html`）打开给学员看——**不用解释，一眼就懂**。

**为什么这时候讲**：**痛点的说服力来自数字，不来自形容。** 说"很难看"学员会点头但没感觉；说"这块版面上有 23.3% 是空的"，他下次自己就会先量。

**互动提问**：这 2,262px 的空白，能不能靠"把图裁成一样高"消掉？（答：能，但你**裁掉的是作品本身**——对作品集是致命的。这条下面第 5 段还要回扣。）

---

## 第 3 段 · 简单版：CSS `columns`（7 分钟）★手册第一条路

**讲什么**：手册给的"简单版"。**它简单到什么程度？关键就三条 CSS**（其余几行全是响应式和列数切换）：

```css
#board       { column-count: 3; column-gap: 20px; }   /* ① 几列 ② 列间距 */
#board > *   { break-inside: avoid; margin-bottom: 20px; }  /* ③ 卡片不许被拆到两列 */
```

（本案例实际用的是 `--gap: 20px`，和核验里量到的"同列间距全部 20px"对得上。）

现场改 `column-count`（2 / 3 / 4）看它怎么自动重排。

**但这一段真正的价值是讲清它的"代价"**（手册只说"简单版"，没说代价）：

1. **顺序被拆掉了**：`columns` 是**竖向填充**的——先把第一列塞满，再塞第二列。所以 DOM 里的第 1、2、3 张图，在屏幕上可能是**一列的上下三张**，而不是"一行三张"。做作品集还行，做"按时间倒序的信息流"就会乱。
2. **追加内容会整版跳**：这是它最大的代价。点"加载更多"加 4 张图，`columns` 会**把全部内容重新平衡一遍**——本案例实测：**16 张旧卡片里有 11 张移动了位置**（数字见 `阶段4` 记录）。用户看着看着，**正在看的那张图会跑走**。

**为什么这时候讲**：这是本案例最容易被跳过、但最该讲的一段。**"简单版"三个字不等于"够用"，它只是"代价换了个地方"。**

## 第 4 段 · 精确版：JS 算每列高度（9 分钟）★手册第二条路 · 本节核心

**讲什么**：手册那句「**JS 计算每列高度，再决定卡片放哪一列**」——把它拆成**三句大白话**：

1. 先知道**有几列**（按容器宽度算）；
2. 维护一个**"每列现在有多高"的数组**（初始全是 0）；
3. 每张图进来，**丢给当前最矮的那一列**，然后把那一列的高度加上这张卡的高度。

就这三句，代码不到 20 行。现场把这 20 行写出来，**不引任何 masonry 库**。

**怎么证明它真的在"填最短列"**：给这段代码加一行"记账"——**每次分配前，把各列高度和目标列都记下来**，暴露成 `window.__masonryDebug`。然后核验脚本逐条校验：**每一次 `target` 是否等于分配前各列高度的 `argmin`**。

**这一段要对比着讲的，还是"代价"**（和第 3 段的 `columns` 对着看）：

| | CSS `columns` 版 | JS 算高版 |
|---|---|---|
| 代码量 | 3 行 CSS | ≈ 20 行 JS + resize 处理 |
| 追加 4 张图后，旧卡片移动数 | **11/16（会跳）** | **0/16（原地不动）** |
| 内容顺序 | 被拆（按列填充） | 可控 |
| 什么时候用 | **页面内容基本固定**、只求快 | **会往下加内容**（信息流 / 作品持续更新） |

**互动提问**：为什么 JS 版追加时旧卡片能不动？（答：因为它**只给新卡片挑列**，从不回头重排已经放好的东西——这正是"最短列优先"这个算法的副产品。）

## 第 5 段 · 三种交互与加载状态（6 分钟）★P08 红线

**讲什么**：手册 P08 那句判据——**"交互是让用户知道'可以做、做完了、出错了'"**——把它落到这个页面上：

| 交互 | 让用户知道什么 | 本案例怎么做 |
|---|---|---|
| **悬停反馈** | "**可以做**" | 卡片抬升 + 图轻微放大 + 底部滑出遮罩，露出"**客户 · {client}**" |
| **加载状态** | "**还没好** / **做完了** / **出错了**" | ① 首屏骨架屏（shimmer）→ 内容替换；② 图片 `decode()` 后 `opacity 0→1` 淡入；③"加载更多"有 **加载中 / 完成 / 失败重试** 三态 |
| **瀑布流** | "还有更多，往下翻" | 本身就是 |

**这一段最该讲的一个反直觉点**：

> **在瀑布流页面里，"加载状态"不是锦上添花，是必需品。**
> 因为卡片高度依赖**图片的真实尺寸**——图没加载完，**根本没有正确的高度可算**。所以骨架屏和淡入不只是好看，它是在**告诉用户"还没好，别急着判断这版排得乱"**。

**还有一个假交互要现场拆穿**：只写 `:hover{ ... }` 就宣称"有 hover 反馈"不够——核验脚本会**真的把鼠标移上去**，对比前后 `getComputedStyle` 的 `transform` 和遮罩 `opacity`，**必须有可见变化**；也**不允许**用 `display:none` 把整张卡藏掉来伪装。

**这一版还有一个必须讲的设计决定（是本案例被独立审查打回后改出来的）**：

> **hover 露出来的信息，必须是"真实且别处没有的"，而且不能承诺做不到的事。**

- ❌ 第一版把卡片写成 `<a href="#">`、hover 文案写"**查看作品**"——可这一页**根本没有作品详情页**。点一下只把 `scrollY` 打回 0、URL 变成 `...html#`：**"查看作品"是一句假承诺**，也是审查配置里的"占位假链接"。
- ✅ 改法很轻，但思路要讲：① 没有详情页就**别伪装成链接**（`.shot` 从 `<a href="#">` 改成 `<div tabindex="0" role="group">`；`tabindex="0"` 让键盘也能聚焦，顺带修掉"`tabindex="-1"` 让 `.card:focus-within` 成为死代码"）；② hover 文案改成 **"客户 · {client}"** —— `client` 本来只躺在 JSON 里，**hover 才第一次露出来**，反馈因此有了真实目的。
- **这条正好回扣 P08 那句判据**："交互是让用户知道'可以做'"，而"可以做"的前提是**这件事真的做得了**。

## 第 6 段 · 核验与收束（5 分钟）★红线

**讲什么**：**"我打开看了眼，挺整齐的"不算证据。** 这个案例尤其如此——

> **"是不是真瀑布流，从截图上分不出来。** 一版把这些图**裁成等高**的假瀑布流，截图看着同样整齐。"

现场跑 `verify_masonry.mjs`（headless Chrome + CDP），逐条读数：

| 验收点 | 怎么证的（不是"看着像"） |
|---|---|
| 卡片高度真的不一 | 量全部卡片 `offsetHeight`，**去重后 ≥ 8 种**，最高/最矮 ≥ 1.5 |
| 真的填最短列 | 校验 `__masonryDebug` 每条 `target == argmin(heightsBefore)`；再量渲染后各列总高极差 |
| 无错位 | 全部卡片包围盒**两两求交，面积必须为 0** |
| hover 有反馈 | 真的派发鼠标事件，比对前后 computed style |
| 加载状态 | 探针查骨架屏数量变化、图片 `opacity`、加载更多三态 |
| 两条路的代价 | 点"加载更多"，数**追加前已存在卡片里有多少张 `top/left` 变了** |
| 手机可读 | 390px 量 `innerWidth / scrollWidth`；**再把 `overflow-x` 摘掉重测一遍** |

**两个必讲的坑**（都是本案例真实会踩的）：

1. **`overflow-x:hidden` 会把横向溢出藏起来。** 量 `scrollWidth === innerWidth` 会以为没事，其实内容被裁掉了。
   → 判据里专门加一步：**用 `!important` 把 `overflow-x` 摘掉，再看 `doc.scrollWidth` 还等不等于 390。**
2. **Chrome 移动端会 shrink-to-fit 骗过你。** 内容溢出时它不产生横滚条，而是把视口撑大：目标 390，`window.innerWidth` 可能报 400+。
   → 判据必须加一条：**`innerWidth` 必须等于目标宽度**，不能只看"有没有横滚"。

**收束**（板书）：这节课的五个数字

| 数字 | 含义 |
|---|---|
| **2,262px / 23.3%** | 普通网格的代价——这就是"为什么要瀑布流" |
| **0.517 ~ 1.786**（3.46×） | 素材长宽比的跨度——痛点从这来 |
| **3 行 CSS vs ≈20 行 JS** | 两条实现路线的门槛 |
| **11 张移动 vs 0 张移动** | 两条路线的**真实代价差异**（追加内容时） |
| **13 种高度 / 0 重叠** | "真瀑布流"的两条测量判据（实测） |

一句话收束：

> **普通网格让每一行整齐；瀑布流让整版好看。选哪个不看流行，看你的图长短一不一致、你的页面会不会往下加东西。**

---

## 板书：三句话

1. **素材先量后做**——长宽比跨度决定要不要瀑布流。
2. **两条路不是"简单/高级"，是"两种代价"**——固定内容用 `columns`，会加内容用 JS。
3. **"真瀑布流"只能被测量证明**——高度够不够散、有没有进最短列、有没有重叠。

## 常见追问

- **"能不能直接用现成的 masonry 库？"** → 能，但本案例刻意不引：它为的是让学员看懂"最短列优先"这 20 行，而不是调一个黑盒。库里做的事情，和这 20 行是同一件事。
- **"为什么不用 `aspect-ratio` 把卡片拉齐？"** → 拉齐就把瀑布流退化成普通网格了（还多留空洞）；真要拉齐，等于放弃了这案例要解决的痛点。
- **"手机上一列还是两列？"** → 一列。手机上列数越少越好读；两列会让每张图很窄，作品细节看不清。
- **"为什么图片用自绘 SVG 而不是真图？"** → ① 零版权风险、零外部请求（保证"发出去就能开"）；② 长宽比可以精确控制成"混排"，把痛点造得准。**真做自己的作品集时，把 `works.json` 里的图换成自己的图即可，代码一行不用改。**

# 讲课大纲 · 案例编程-06 数据看板 / 运营后台页

> 手册只给了主题（"生成数据看板、运营后台和高信息密度业务界面"），本大纲把它展开成可直接讲的 6 段。
> 面向学员的话术已写成"能直接念"的口吻。

---

## 这节课要学员带走的判断

**看板的竞品不是别的看板，是"Excel + 印象"。**
所以它的验收标准不是"图表好不好看"，是一个行为问题：**你明天会不会再打开它？**
打开 = 痛点解决了；不打开 = 做得再漂亮也是废的。

**第二判断：先定问题，最后才定颜色。**
dataviz 这套方法把顺序钉死了：**先决定"读者要完成什么判断" → 再选图形 → 再分配颜色 → 最后跑校验器验证配色**。绝大多数难看的看板，错在跳过了第一步。

---

## 第 1 段 · 把"想看一眼"翻译成 6 个数字（5 分钟）

**讲什么**：开工前先回答"老板早会上会问哪几句"。现场写在板上：

> 1. 总共卖了多少？ → **本期净销售额**（hero）
> 2. 比上期好还是差？ → **较上期 ±%**
> 3. 卖了多少单、几个人来、多少钱一单？ → **订单数 / 访客数 / 客单价**
> 4. 转化行不行？ → **支付转化率**
> 5. 有没有漏水？ → **退款率**
> 6. 新客沉淀了吗？ → **新增会员**

**为什么这时候讲**：**这 6 个数字不是"指标越多越好"堆出来的**，是"老板只问这几句"倒推出来的。看板第一屏放不下的指标，就该放到第二屏或明细表里。
**互动提问**：如果你老板从来不问"新增会员"，这一格该留吗？（答：撤掉。**空着比填错更诚实**——留一格没人看的数字，等于每天都在用一格的注意力交税。）

**工具理性的坑（要点名）**：学员这时候最容易问"用什么框架""要不要接数据库"。**回到痛点**：这个看板要解决的问题是"5 秒内看到答案"，不是"建一套数据中台"。**单文件 HTML 秒开、离线能看、随手能发**——这正是它赢过 BI 的地方。

## 第 2 段 · 先选形态，最后才选颜色（6 分钟）★本案例的方法核心

**讲什么**：现场打开 `dataviz` 的 `references/choosing-a-form.md`，逐条对：

| 数据的任务 | 该用 | 不该用 |
|---|---|---|
| 一个当前值（+环比） | **stat tile（KPI 磁贴）** | 一根柱的柱状图 |
| 几个头条数字 | **KPI 行** | 分组柱状图 |
| 一条趋势 | **折线** | 饼图 |
| 5 个渠道比量级 | **条形（单色）** | 彩虹色 / **按数值深浅上色** |
| 品类占多少（部分-整体） | **100% 堆叠条** | 饼图（>6 段就更糟） |
| "谁在拖后腿"（40 个 SKU 都要有意义） | **表格**（或表 + 图） | 40 种颜色 |

**这一段最该讲的一个反模式**：**"数值色阶套在名义类别上"**——渠道名字（自然搜索/信息流/私域…）之间**没有大小顺序**，把柱子按销售额深浅上色，等于**用颜色重复说了一遍柱长已经说过的事**，还烧掉了唯一一条自由通道（颜色本该用来区分身份）。**正确做法：一个系列 → 一个颜色，所有柱子同色。**

**为什么这时候讲**：学员做看板最常见的动作是"先想配色方案"。**顺序反了。** 颜色是最后一步，而且是**可以计算验证的**——不是"我觉得区分得开"。

---

## 第 3 段 · 配色不是审美，是校验（5 分钟）★本案例的硬技术点

**讲什么**：现场跑 dataviz 的校验器（`阶段3` 里有实测输出）：

```
node scripts/validate_palette.js "#2a78d6,#eb6834,#1baf7a,#eda100,#e87ba4" --mode light
```

它查六件事：明度带 / 色度下限 / **相邻两色的色盲可分辨度（CVD ΔE）** / 常人可分辨度 / 与底色的对比度 / 顺序。

**本案例实测结果**：
- 全 5 槽 **PASS**；
- 最差相邻对 `#eda100 ↔ #1baf7a` **CVD ΔE 9.1**（目标 ≥8）；
- 常人最差相邻对 `#e87ba4 ↔ #eda100` **ΔE 19.6**（下限 ≥15）；
- **1 个 WARN**：aqua / yellow / magenta 三个槽对底色的对比度 **< 3:1 → "relief required"**，即**必须给可见标签或表格视图**。

**这一段最该讲的三句话**：
1. **"这三个色偏浅"不是缺点，是它给你下的一个义务**：浅色不能单独承担表意 → 所以本案例**永远配着图例 + 直接标签 + 一张表格视图**。这就是为什么明细表不是"可有可无的第四块"，**它是配色方案的一部分**。
2. **色盲可分辨度不能眼看**。ΔE 是可以算出来的，**别用"我觉得区分得开"替代校验**。
3. **系列颜色跟着实体走，不跟着排名走**。筛选后剩下的系列**不能重新上色** —— 学会了"自然搜索是蓝色"的人，不能被你的筛选器骗。

## 第 4 段 · 交互的四个"让用户知道"（6 分钟）

**讲什么**：M4 P08 说「交互是让用户知道'可以做、做完了、出错了'」。翻译到看板上是四件事：

| 用户想知道 | 本案例怎么给 |
|---|---|
| **我能做什么** | 过滤器**一整行**放在所有内容之上（不是每个图各配一套）；表头有可点击的视觉暗示与排序方向箭头 |
| **我看到的是什么** | 折线的**十字准线 + 读数窗**：鼠标指到哪一天，**一次列出本期与上期两个值**（读者不必精确命中那 2px 的线） |
| **我做完了** | 切换时间范围，**全页数字一起变**——不是只有一张图变（那样你会以为其他数字是旧的） |
| **出错了/没数据** | 搜索无命中时给**空状态**："没有匹配的商品，试试清空筛选"，而不是一张空白的表 |

**红线纪律（dataviz 明确禁止的两条）**：
- **tooltip 不能是读到数值的唯一途径** —— 每个 tooltip 里的值都必须能从直接标签或表格视图拿到。**tooltip 是增强，不是闸门。**
- **不许双 Y 轴** —— 两个量纲不同的指标想放一起看，就**画两张图**。双轴会凭空造出一个数据里不存在的相关性。

## 第 5 段 · 核验：三条"看起来通过"的假象（7 分钟）★红线

**讲什么**：这一段是本案例踩过的坑，逐条现场演示。

### 假象 1 · "图出来了" ≠ "图画对了"
SVG 里有一个 `<path>` 不等于画对：坐标可能是 `NaN`、可能全在 viewBox 外面、可能只画了 7 个点却说是 30 天。
→ 判据：**几何点必须是有限数、必须落在 viewBox 内、点数必须等于切片数据条数**。

### 假象 2 · "数字变了" ≠ "数字算对了"
切了时间范围看到数字变了，不代表算对了。
→ 判据：拿**独立算出的真值**比对。本案例的做法很硬：
- 阶段 1 用 **Python 写了一份参考实现**（同一套 mulberry32 伪随机 + 同一套公式），生成对照数据集与**逐行 SHA-256**；
- 核验脚本从页面里取出 JS 生成的行数据，用**同样的规范化字符串**算哈希，**和 Python 那边逐字节比**。
→ **"页面数据 == 参考数据"是哈希级的一致，不是"看起来差不多"。**（这一步顺带证明了"固定种子"这件事是真的：换个种子哈希立刻不匹配。）

### 假象 3 · "手机不横滚"可能是被藏起来的
- `body{overflow-x:hidden}` 会把真实溢出**裁掉** —— 看起来不滚，实际内容已经被切了；
- Chrome 移动端遇到溢出会 **shrink-to-fit**：目标 390，`innerWidth` 却报 422，**横滚条根本不出现**。
→ 判据必须两条同时成立：**① 断言 `innerWidth === 390`；② 摘掉 `overflow-x:hidden` 之后再量 `document.documentElement.scrollWidth ≤ 390`。**
（本项目在案例 09 已经踩过这个坑，本案例把判据直接写进核验脚本。）

**为什么这时候讲**：这一步就是编程-12 说的"把'做完了'变成'验收通过'"。**你的核验脚本的质量，决定了你的交付质量。**

## 第 6 段 · 收束：看板要活过三个月（3 分钟）

**讲什么**：
- 现场演示：双击打开 → 一眼看到 hero 与 6 个 KPI → 切"近 7 天"（全页重算）→ 趋势图上扫一下出读数窗 → 点"GMV"表头排序 → 点品类"美妆个护" → 搜一个 SKU 名 → 出空状态。
- 一句话收束：
  > **看板的价值不在它上线那天有多好看，在于三个月后你改口径时，成本是不是还是 0。**
  > 单文件 HTML 的"免部署、免授权、改得起"，才是它活下来的原因。
- 留一个课后动作：**回去把你手上那份"每周要花 40 分钟拼的表"，先只回答"老板会问哪 6 句话"**，其余先不做。

## 板书：这节课的六个数字

| 数字 | 含义 |
|---|---|
| **6** | KPI 磁贴数（由"老板会问哪几句"倒推，不是指标堆砌）|
| **3** | 图表数 / 三种形态（折线 · 条形 · 100% 堆叠条）|
| **40** | 明细表 SKU 数（"谁在拖后腿"必须能下钻）|
| **1** | 过滤器行数（一整行，放在所有内容之上；不是每图一套）|
| **9.1 / 19.6** | 调色板最差相邻 CVD ΔE / 常人 ΔE（≥8 / ≥15 才过）|
| **9.1 → WARN** | 3 个浅槽对比度 <3:1 → 必须配可见标签或表格视图（relief 义务）|

## 常见追问

- **"为什么不直接用 ECharts？"** → 一个 ECharts CDN 包 700KB+，且要联网；本案例的三张图都是**简单的**几何（折线、横条、堆叠条），**手绘 SVG 反而更短、更快、能离线、还能精确控制 mark 规范**（4px 数据端圆角、2px 面色间隙这些细节，第三方库里反而要跟配置打架）。**工具理性陷阱**：为了"专业"引入一个大库，换来的是首次加载变慢和一堆用不上的能力。
- **"为什么明细表也算图表的一部分？"** → 因为配色校验给出了 **relief 义务**（3 个浅色槽对比度 <3:1）。**表格视图是配色方案合规的必要条件**，不是额外功能。
- **"数据是假的，这看板有意义吗？"** → 演示数据的作用是**证明这条流水线是通的**：把 `生成数据()` 换成 `fetch('/api/orders')` 就是真看板。**先证明"打开就有答案"这件事能成立**，接真数据是最后一步、最简单的一步。
- **"改口径真的只要改一行吗？"** → 时间范围是一个变量、指标口径是一段函数；**改 KPI 定义 = 改那段函数**，全页三张图和表格自动跟着变。这就是"边际成本为 0"的具体含义。

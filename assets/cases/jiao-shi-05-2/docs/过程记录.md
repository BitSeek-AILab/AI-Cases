## 二、⚠ 关键数字核对（落实手册"AI算数字出图表，上报前要核一眼"）

本案**不重新算数**——直接复用案例05-1 已复算、已两重核对过的 `analysis.json`。这是刻意的设计：**同一场考试的三份产出必须同源**，各自算一遍必然出现"报告里一个数、表格里一个数"的经典事故。

在本案内做的核对是**"数字有没有被正确搬运进两份报告"**：

| 核对项 | 方法 | 结果 |
|---|---|---|
| Word 报告里的关键数字 | python-docx 提取全文（含表格）后做字符串检索 | `360.4` `419` `283` `77.3` `67.9` `52.5%` `27 人` `136` **全部命中** ✅ |
| Word 附表一与"各科统计"页一致 | 表头 7 行 × 8 列逐项比对 analysis.json | 完全一致 ✅ |
| Word 三类名单人数 | 表格行数 6 / 17 / 13 | 与三类判定口径实算一致 ✅ |
| HTML 里的关键数字 | 生成脚本直接从 analysis.json 取值（**无手抄环节**） | 结构性保证一致 ✅ |
| 薄弱点解读与手册逐条对照 | 5 科不及格人数与百分比 | 与手册**逐条一致**（19/47.5%、14/35.0%、13/32.5%、7、6） ✅ |
| 与手册的两处已知数字错 | 400分以上、偏科人数 | 本案例沿用案例05-1 的更正结论（7 人、27 人），**未沿用手册的 6 人与 7 人** ✅ |

> 结论：**手册"核一眼"的建议在第二步尤其重要**——第二步最容易把第一步的错数字"顺下去"。本案因为强制同源，把这种风险掐掉了。

## 四、技术处理与踩到的坑

1. ⚠ **坑1 · 本机无 LibreOffice**：`docx` skill 规定的渲染核验路径（`soffice` → PDF → `pdftoppm`）走不通。
   **对策**：改用本机已装的 **Microsoft Word 16.0 COM** `ExportAsFixedFormat` 导 PDF，再用 PyMuPDF 转 PNG 目视。**【替代】**
2. ⚠ **坑2 · 视觉 MCP 无有效凭据**：`agent-vision` 返回 `❌ API 密钥无效（401）`。
   **对策**：改用 Read 直接读取截图目视核对（Read 支持图片）。**【替代】**
3. ⚠ **坑3 · Word 导出的 PDF 被 Read 判为"受密码保护"**：直接用 Read 打不开该 PDF。
   **对策**：用 PyMuPDF 把 PDF 逐页栅格化成 PNG 再读。**（绕开的做法：pymupdf 转图）**
4. ⚠ **坑4 · node 的 `NODE_PATH` 未生效**：试图复用第06章 case 的 `node_modules` 失败（且该目录随后被清理）。
   **对策**：在 `_work/docxbuild/` 内 `npm install docx` 本地安装（22 个包，10 秒）。
5. ⚠ **坑5 · JS 字符串里的中文引号**：把中文里的 `"吃不饱"` 用 ASCII 双引号写进了双引号字符串，直接 `SyntaxError`。
   **对策**：中文内嵌引号统一改全角 `“ ”`。
6. **单文件离线的取舍**：手册要求"适合发家长看"，故**不使用任何 CDN**（不引 ECharts/Chart.js/字体），图表全部手写内联 SVG。代价是代码量大，收益是家长点开必能看到图（不依赖网络与第三方可用性）。
7. **暗色模式**：按 `dataviz` 的 palette 文档，在 `prefers-color-scheme` 与 `[data-theme]` 两个作用域分别给值，而非自动反转色值。
